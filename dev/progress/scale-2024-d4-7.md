# Scale evaluation — 2024 d4–7, qwen2.5-coder:7b, self-consistency (samples=3)

First measurement beyond the d1–3 baseline. The winning self-consistency config
(`samples_per_model=3`, `temperature=0.7`) run on the 8 problems we had never scored, all
cached with oracle answers so the run is fully verified offline. 1 trial, 109 min wall
clock. Artifact (gitignored): `dev/experiments/20260812T180451Z_scale-samp3_a6f101eadf5f.json`.

## Result: the win does NOT generalize to harder problems

```
                solved  rate   attempts (samples=3)
2024 d4–7       1/8     12%    51: 30 error / 20 wrong / 1 solved
```

Only **2024 d6 p1** solved (guard-patrol simulation) — now recorded and verified
(`solutions/2024_day06_part1.py`, `dev/verify_solutions.py` 5/5). The other seven are
unsolved even with three samples each.

This is the sharpest evidence yet on the project's oldest open question — *"are the 7B
models too weak?"* — and the answer is now measured, not assumed: **qwen2.5-coder:7b solves
the easy end of AoC 2024 (d1–3, reliably, with self-consistency) but hits a hard capability
ceiling by d4–7.** Self-consistency reduces run-to-run *variance* on problems the model can
already sometimes solve; it cannot manufacture capability the model lacks. More samples gave
more shots and the extra shots simply failed the same way.

## Two distinct ceilings

Per-problem, the failures split cleanly:

| problem     | outcome       | answers produced | reading |
|-------------|---------------|------------------|---------|
| d4 p1       | no_candidate  | 0                | can't produce runnable code |
| d4 p2       | no_candidate  | 6 (all wrong)    | runs, wrong reasoning |
| d5 p1       | no_candidate  | 0                | can't produce runnable code |
| d5 p2       | no_candidate  | 0                | can't produce runnable code |
| d6 p1       | **solved**    | 1                | ✓ |
| d6 p2       | no_candidate  | 6 (all wrong)    | runs, wrong reasoning |
| d7 p1       | no_candidate  | 7 (all wrong)    | runs, wrong reasoning |
| d7 p2       | no_candidate  | 1 (wrong)        | runs, wrong reasoning |

- **Can't-code-it (30/51 error, 59%):** the model fails to emit runnable code at all.
  8 of those 30 are still the "no `solve()` function" wrapper miss — the D-diagnosis
  category the prompt hardening targeted, so **the hardening did not eliminate it on hard
  problems** (a genuine, if unwelcome, data point on that unmeasured change).
- **Wrong-reasoning (20/51 wrong, 39%):** the model emits runnable code that produces a
  confident, wrong answer. d4 p2, d6 p2, and d7 all sit here.

Zero regression into overfit; the oracle held.

## What this means for the roadmap

The bottleneck for *broader coverage* is **model capability, not orchestration.** The
platform has now measured the reachable frontier of this model: self-consistency makes the
easy problems reliable, and past that the 7B is genuinely out of depth. The levers that would
move d4–7 are:

1. **A stronger model** — the direct test, but **hardware-blocked**: qwen2.5-coder:32b swaps
   on 16 GB (120 s timeout for 40 tokens); phi4 / qwen3.5:9b run but at ~5 min/generation a
   full self-consistency sweep is 8 h+. This is the single highest-value experiment the
   platform cannot currently run — it needs more RAM.
2. **More samples** won't help the wrong-reasoning problems (the model is confidently wrong,
   so a plurality of wrong candidates would still lose), and won't help the can't-code-it
   problems (nothing to vote on).

The honest conclusion: the *platform* is working exactly as intended — it turned "the 7B is
too weak" from an assumption into a measured frontier, and it separates variance-limited
problems (fixable with sampling) from capability-limited ones (needing a better model). The
AoC-solving *ceiling* on this hardware is real and now quantified.

## Reproduce

```
venv/bin/python experiment.py --problems 2024:4-7 --trials 1 \
  --config "name=scale-samp3,models=qwen2.5-coder:7b,temperature=0.7,samples_per_model=3"
```
